# Первый backend frontend harness

Это отдельный маленький devtool для оценки Linux backend. Он не входит в Electron renderer и не требует React, Vite или node-pty: Node запускает `phantom-backend` как дочерний процесс, браузер получает простую панель через локальный HTTP server.

Из корня репозитория:

```bash
mkdir -p /tmp/phantom-harness-workspace
node tools/frontend-harness/server.mjs \
  --backend backend/out/linux-debug/phantom-backend \
  --workspace /tmp/phantom-harness-workspace
# открыть http://127.0.0.1:4177
```

Проверки стенда без браузерных зависимостей:

```bash
node tools/frontend-harness/ui-smoke.mjs
node tools/frontend-harness/interactive-ui-smoke.mjs
node tools/frontend-harness/output-ui-smoke.mjs
node tools/frontend-harness/live-ui-smoke.mjs backend/out/linux-debug/phantom-backend
node tools/frontend-harness/smoke.mjs backend/out/linux-debug/phantom-backend
```

`--workspace` должен существовать или быть создан заранее. Backend сам создаёт `.phantom/backend-build`; исходник из поля редактора отправляется как immutable `main.cpp` snapshot.

Стенд использует тот же wire protocol: `connect`, `build`, `launch`, `step`, `continue`, `pause`, `stop`, `getState`, `listHistory`, `appendInput`, `closeInput`. Он показывает состояние, observation, переменные с адресами storage, оба потока вывода, ошибки и события/ответы NDJSON. Кнопка «Перезапустить backend» завершает дочерний процесс и начинает новую сессию. Для аргументов и environment используются отдельные строки; пробелы внутри значения сохраняются.

`interactive-ui-smoke.mjs` запускает `app.js` в изолированном VM без браузера и проверяет две последовательные остановки на `cin`, точные подтверждённые фрагменты, незавершённый токен, опережающий `commandFinished` response race, повтор append с тем же ID после временной ошибки, редактирование черновика во время передачи, EOF, запрет пустого append, ручной ввод после Get state/Pause и отсечение запоздалого HTTP-ответа после reset. `live-ui-smoke.mjs` выполняет настоящий `app.js` через HTTP server и GDB: два ожидания `cin`, точные фрагменты, `getline` и EOF.

После запуска открытого stdin поле «Черновик будущего ввода» работает как локальный редактор Phantom. Текст не отправляется целиком заранее: режим `Пробел/Enter` подтверждает первый токен, режим `Только Enter` сохраняет пробелы для `getline`, а ручной режим вообще не подаёт данные автоматически. Backend получает подтверждённый фрагмент только в состоянии `waitingForInput`/`input-wait`; после успешного append тот же `step` или `continue` возобновляется ровно один раз. После обновления страницы или Pause доступны ручные append/EOF; исполнение продолжается только явным нажатием Step/Continue, поскольку незавершённая команда уже не принадлежит этому окну. Кнопки «Подтвердить токен» и «Подтвердить строку» остаются ручным способом выбрать границу. «Завершить ввод (EOF)» и Ctrl+D сначала передают весь оставшийся черновик, включая незавершённый токен, затем закрывают stdin. Уже переданные диапазоны и semantic `consumedRanges` показываются отдельно; в native `transport-only` consumed честно отображается как `ND`.

Поле «Вывод программы» объединяет уже сброшенный stdout и **красные несброшенные фрагменты** выбранной остановки. Метрики pending/window/free/storage находятся в раскрываемом блоке «Буфер и ёмкость». Поддержан стандартный Linux x86_64 libstdc++ `cout`, включая `sync_with_stdio(false)`: `stdout.coutBuffered` описывает его реальный буфер. C `stdout.buffered` остаётся отдельным снимком; при синхронизации это один буфер и он показывается один раз. Если `printf` и несинхронизированный `cout` одновременно имеют pending-байты, они подписаны отдельно: будущий порядок flush неизвестен.

Профиль проверяет ABI, настоящий `rdbuf`, codecvt и принадлежность fd 1 транспортному pipe. Custom/null/перенаправленный буфер, пользовательское преобразование кодировки и остановка внутри runtime возвращают явную недоступность. Вызовы inferior для чтения/flush не выполняются. Подтверждение ABI проверено на установленной libstdc++13; libc++ и другие layouts требуют отдельных профилей. Свободное место не обещает момент flush. Уже сброшенный текст не стирается при просмотре более раннего снимка; он отмечается как полученный позже выбранной точки. В этом окне используется локальное представление журнала. Backend дополнительно предоставляет `readOutputJournal` для точных байтов, пропусков хранения и границы выбранного снимка; стенд пока не загружает его страницы автоматически. Отмена внешнего вывода не поддерживается.

«Карта виртуальной памяти» показывает `observation.memoryMap`: реальные диапазоны `/proc/<pid>/maps`, права, пути и вид области. Там присутствуют и read-only области с таблицами виртуальных функций; автоматическое распознавание vtable/типов пока запланировано. Содержимое получает frontend через существующий `readMemory` с актуальным `expectedStop`, адреса передаются hex-строками. Поле `coverage` сообщает полноту самой карты; оно не означает, что bytes всей памяти захвачены. Недоступность procfs не ломает исполнение.

Новые backend-команды для регистров, `/proc`, ELF-модулей, секций/символов и структуры переменных по DWARF, чтения vptr/vtable в выбранном ABI-профиле, журнала вывода, снимков/сравнения памяти и instruction trace описаны в [INSPECTION_GATEWAYS.md](../../docs/INSPECTION_GATEWAYS.md). Они доступны через протокол и `/api/request`; отдельных кнопок для них в этом стенде пока нет. Будущая карта памяти — 2D, её renderer делает frontend-агент. После пересборки уже запущенный backend нужно перезапустить кнопкой стенда, чтобы он сообщил новые capabilities.

Для проверки выбери пример `cout: sync_with_stdio(false)`, выполни Build/Launch и проходи Step: сначала красный `cout: pending`, затем независимый `printf: pending`, затем их последовательный flush. `output-ui-smoke.mjs` проверяет shared-buffer dedup, независимые буферы, HTML escaping, переход pending→flushed и просмотр исторического pending.

Журнал событий читается курсором через `/api/events?after=N`. Если сервер сообщает `gap`, часть журнала уже вытеснена; после этого нужно запросить `Get state` и не считать пропущенную команду успешно завершённой. Стенд рассчитан на одну активную вкладку: несколько вкладок используют один backend и могут менять общую сессию.

После полной перезагрузки страницы журнал ввода восстанавливается из снимка
последней остановки. Если вручную подать данные или EOF и перезагрузить страницу
до следующей остановки, этот исторический снимок ещё не содержит изменения;
продолжение процесса создаст актуальный снимок. Неотправленный локальный черновик
при перезагрузке страницы не сохраняется.

## Что проверить вручную

1. Build и Launch: после Launch дождись `state.phase=stopped`, проверь `stop.reason=entry`, source location и `processInstanceId`.
2. Step/Continue/Pause/Stop: порядок `accepted`, `observation`, `state`, `commandFinished`; после Stop должны сохраниться stdout и stderr. Для долгого Continue кнопка Pause остаётся доступной.
3. Введите Unicode, `NUL` нельзя вставить обычным textarea; проверьте большие строки через отдельный тест backend.
4. Укажите аргументы и environment по одному на строку (`KEY=value`), убедитесь, что они доходят до программы.
5. History после нескольких остановок: панель покажет номера остановок, их label и `stopId`; это индекс снимков, а не перемотка процесса.
6. Закройте backend или нажмите Restart во время операции: UI должен показать ошибку/новую сессию, а не продолжить старое состояние.
7. Переполните журнал большим числом событий: после `gap` состояние нужно сверить через `Get state`.
8. Оставь флажок конечного ввода выключенным, запусти программу, ожидающую `cin`, набери в черновике `12 34` и проверь, что пробел автоматически подтверждает только `12 `, а остальная часть остаётся редактируемой. Проверь состояние `waiting`, exposed/consumed ranges и то, что `deliveredBytes` не выдаётся за число извлечённых значений. Для `getline` введи строку и подтверди её Enter без подмены пробелов.
9. Проверь Ctrl+D во время ожидания открытого stdin: должен появиться `eof: requested`. Это запрос закрытия потока; native-профиль не утверждает, что C++ уже прочитал EOF. Пустой черновик сам по себе EOF не означает.
10. Для `while (true) { continue; }` Step не может найти следующую source line: через короткий timeout появится `step-timeout`/`STEP_TIMEOUT`, сессия останется живой. Используй Continue → Pause или instruction step.

Отдельный opt-in профиль `gdb-record-full` теперь даёт обратный шаг и переход к записанной инструкции через протокол; настройки launch и кнопки этих команд в стенд ещё не добавлены. Профиль требует конечного stdin и поддерживает только инструкции/системные вызовы, которые умеет записать установленный GDB. Команды, ограничения и `probeRecorders` описаны в [RECORDING.md](../../docs/RECORDING.md). Обычные кнопки стенда сохраняют native-исполнение с интерактивным вводом.

Это диагностический стенд: запись переменных и verified restore по-прежнему выключены; runtime-адрес и raw storage переменных показываются только при безопасном подтверждении GDB.

События harness читаются курсором: `/api/events?after=N` возвращает только записи
после `N`, `nextCursor` и признак `gap`. Это предотвращает потерю событий при
параллельных запросах одного клиента; при `gap:true` нужно заново запросить
state и не считать пропущенную команду успешно завершённой.

Для следующей интеграции frontend доступен `writeMemory`: проверяемая запись
до 256 raw bytes в native-процессе, audit результата и ветви истории. Кнопки
редактирования в этот стенд пока не добавлены; типизированная запись переменных
остаётся выключена. Формы запросов, получение audit и ограничения приведены в
[INSPECTION_GATEWAYS.md](../../docs/INSPECTION_GATEWAYS.md#checked-native-memory-interventions).

Через протокол также доступны `inspectScalarStorage` / `writeScalarStorage`:
целые 8/16/32/64 бит и bool с проверкой настоящего GDB-типа, адреса и исходных
байтов. Начните с inspection текущего locator и используйте полученный
snapshotId; пример — в [контракте](../../docs/INSPECTION_GATEWAYS.md#typed-scalar-storage).
Явный `profile:"native-dwarf-scalar-v2"` в inspection и записи добавляет
`float`/`double`: `rawBitsHex` хранит точный битовый рисунок, включая знак нуля
и payload NaN. Доступность профиля — в `capabilities.scalarStorageProfiles`.
Кнопок этой операции в стенде пока нет. Это typed storage-профиль с lifetime
unknown; старый `writeVariable` остаётся выключен.
